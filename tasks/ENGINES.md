# Engines Roadmap

Tactical, snapshot-by-snapshot status for the engines track. For the design (roles, layout,
evidence rules, draft schema, phases), see [`../docs/engines/overview.md`](../docs/engines/overview.md).
Model status stays in [`ROADMAP.md`](./ROADMAP.md).

## Current focus

**Phase:** **E5 done** (engine schema v3): NVIDIA's training stack joins as two snapshots,
[`megatron-lm-core_v0.19.0`](./engines/megatron-lm-core_v0.19.0.md) and
[`megatron-bridge-v0.6.0`](./engines/megatron-bridge-v0.6.0.md), both released 2026-08-19. Six
engines now feed the support matrix, and "Implemented by (engines)" sections cover 15 glossary
entries.

**Next:** maintenance mode. Take the 2026-Q4 snapshot at quarter end, or refresh on demand; the
adoption report's "Still missing" list is the refresh queue. Worth rechecking first:

- SGLang and VeOmni for Qwen3.8-Flash-Next.
- Every engine for GLM-5.3-Flash and DeepSeek-V4.1-Flash.
- Megatron-LM: does DeepSeek-V4 reach a release, and does Megatron-Bridge pin one?

What E5 showed:

- **Megatron-LM has no model registry; Megatron-Bridge is the registry.** Engine schema v3 adds
  `support: delegated` + `delegated_to` for this: Megatron-LM keeps docs-signal
  `model_specific` rows (DeepSeek-V3, Qwen3, Qwen3-MoE) and delegates the other 12 architectures
  to `megatron-bridge-v0.6.0`. The matrix shows Bridge's support through the delegation, and
  delegated rows never enter the "Still missing" list.
- **The DeepSeek-V4 training chain rests on unreleased code.** Megatron-Bridge registers
  DeepSeek-V4 (CSA/HCA, mHC, hash MoE, MTP), but the Megatron Core modules are on Megatron-LM
  `dev`; neither Bridge's submodule pin (`cd4afff`, a `main` commit) nor `core_v0.19.0` has them.
  verl's MTP path for DeepSeek-V4 goes through exactly this chain.
- **Bridge pins Megatron-LM by submodule commit, not by release.** The same-day Megatron-LM
  release sits on a release branch that `main` does not contain.
- **CSA/HCA gets its first engine assertion** (Megatron-Bridge, via dev-branch Megatron Core), and
  GLM-5.2's IndexShare now has training-side implementations in both Megatron snapshots.
- **Megatron-LM claims all three roles**: training (core), GRPO-only Megatron-RL, and an
  inference engine with an OpenAI-compatible server. Synthesis now groups snapshots by primary
  role (listed first), so it sits with the training engines.

**E4 done**: the first engine synthesis is generated by `synthesis.index` and checked for
staleness in CI: [`engine-support-matrix.md`](../data/reports/engine-support-matrix.md) (models ×
snapshots, techniques × snapshots), [`engine-adoption.md`](../data/reports/engine-adoption.md)
(month-precision support lag) and the glossary "Implemented by (engines)" sections.

What E4 showed:

- **Commodity techniques are blank by scope.** GQA, YaRN and FIM show no engine rows because
  snapshots only assert model-specific or recent techniques. Blank means "not asserted".
- **Model-side techniques with no engine assertion yet:** CSA/HCA, CSA2, QSA, INT4 QAT,
  N-gram embedding, AttnRes, gated residual, DCA and CED. Each is a question for the next refresh:
  is it implemented under another name, in a dependency, or absent?
- **Registry engine slots were not needed.** `glossary_slug` is already validated against
  the registry.

**E3 done**: all four tracked engines have a 2026-Q3 snapshot (engine schema v2).

E3 added the training and RL role subobjects, and replaced `in_native_registry` with a
three-level `support` because verl has no model registry. First training/RL findings, detailed
in [`engines/verl-v0.9.0.md`](./engines/verl-v0.9.0.md) and
[`engines/veomni-v0.1.12.md`](./engines/veomni-v0.1.12.md):

- **verl's rollout pins do not match our inference snapshots.** It requires `vllm>=0.18.0` but
  its Docker image tests 0.24.0, five minor versions before `vllm-v0.29.0`. For SGLang the
  sources disagree (`setup.py` 0.5.8, Docker 0.5.12, docs 0.4.8), and none matches
  `sglang-v0.5.19`.
- **The two training frameworks cover models differently.** VeOmni registers DeepSeek-V3/V4,
  GLM-5.x and the Qwen3/3.5 family. verl carries model-specific code for DeepSeek-V4 (keyed on
  model_type, Megatron + vLLM) and Qwen3.5. Neither has Kimi K2.5/K3, Qwen3.8-Flash-Next,
  DeepSeek-V4.1-Flash or GLM-5.3-Flash.
- **MTP training is narrow.** verl supports it only on Megatron-Bridge + Megatron, and VeOmni
  drops DeepSeek-V4 MTP weights at load ("MTP not supported for now").

**E2 done** (`sglang-v0.5.19`).

**E1 (pilot) done.** Engine schema v1, the `extract-engine` skill, the

## Snapshot policy

- **Quarterly.** At each quarter's snapshot, take the latest non-prerelease upstream tag for
  each tracked engine.
- **On-demand refreshes** in between, for three triggers only:
  - A newly extracted model needs engine-side support recorded.
  - A release changes a role subobject.
  - A synthesis question needs a version no snapshot has.
- Snapshots accumulate under their own slugs (`<engine>-<release-tag>`); none is overwritten.

## Seed questions for the pilot

These come from existing model records. They check that the schema can close real gaps; they
are not a to-do list. **Outcomes for `vllm-v0.29.0` are in
[`engines/vllm-v0.29.0.md`](./engines/vllm-v0.29.0.md)**:

- V4.1-Flash is absent at this tag.

- DSpark is implemented, but the γ mismatch is unresolved.

- DSA and IndexCache are implemented; CSA/HCA is not asserted.

- The parser gap is on the engine side too.

- **DSpark.** `deepseek-v4-flash-0731` records vendor serving flags for vLLM
  (`--speculative-config '{"method":"dspark"}'`) and SGLang (`--speculative-algorithm DSPARK`).
  Which engine versions implement DSpark, and does either engine document the
  `num_speculative_tokens: 7` vs trained γ=5 mismatch?

- **DeepSeek-V4.1-Flash.** Its record says no serving command was published. Does
  `vllm-v0.29.0` (released the day before V4.1) or a later snapshot list
  `DeepseekV41ForCausalLM`?

- **Sparse attention.** DSA (DeepSeek-V3.2-Exp, 2025-09), CSA/HCA (DeepSeek-V4) and IndexShare
  (GLM-5.2) all have glossary entries. (`vllm/docs/design/hisparse.md` turned out to post-date
  `v0.29.0`; it belongs to the next snapshot.)

- **Reasoning and tool parsers.** Model records note that no `--tool-call-parser` flag is
  published for DeepSeek-V4 / V4.1. The engine's parser registry is the authoritative place to
  check.
